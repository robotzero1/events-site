# events-site

The public website of the events listing: plain PHP 8.2+ with Twig, building every page on the server from the events API, which is in a private repository (`robotzero1/Events`, checked out as `../Events`). This repository is public, as a portfolio piece: nothing secret goes in it, nor anything that would help someone abuse the site, nor links into the private repository. The spec is issue #1; the tickets are #2 to #12. How to run and test it is in `README.md`.

## Decisions

- **Two layers.** The core (`src/`, `templates/`, `lang/`) knows nothing of where it runs; the standalone layer (`standalone/`, `public/`) runs it on its own and is what a WordPress plugin is to replace. Anything WordPress would do differently (asking over HTTP, keeping answers, logging, the page frame, sending a response) is behind an interface or in the standalone layer. The core gives back an `Answer`.
- **No framework.** Composer is for autoloading, Twig and PHPUnit only. Written for PHP 8.2 (`config.platform` in `composer.json` holds the lock to it): no PHP 8.3+ features.
- **Addresses are `Addresses`**, in both languages, the words translated (`/es/evento/{ref}`, `/en/event/{ref}`) and a listing's filters too (`desde`, `from`). A page is found by the name `Addresses` gives it, in `Site::pages()`. An address that is no page, or that names what the API does not have (`NotThere`), is a 404 in the address's language.
- **The bare `/`** is a 302 to the browser's language (`Language::preferredBy()`), Spanish otherwise; `/es` and `/en` are a 301 to `/es/` and `/en/`.
- **A page asks the API only through `Api\Asking`**, with a lifetime: `REFERENCE_LIST` (an hour), `LISTING` (five minutes), or null for a Search, which is never kept so that each is counted in the API's Search log. An answer is kept a day past its lifetime (`GRACE`) and used when the API fails, which is logged; with nothing kept the page is `Unavailable`, a 503 with `Retry-After` and `noindex`.
- **Every request to the API** carries `Accept-Language` and the visitor's address in `X-Forwarded-For`, which the API believes from the server itself alone.
- **Twig escapes everything** (`autoescape`, `strict_variables`); the one `|raw` is the frame putting in a page's content, which its own template made. What visitors and other websites wrote is never put in as HTML.
- **Every word the site says** is in `lang/es.php` and `lang/en.php`, with the same keys (a test holds them to that), through `t()` in a template and `Strings` in PHP.
- **Everything is inside one `<div class="events-site">`**, so that a WordPress theme and the site's CSS leave each other alone.
- **The look is Almanaque** (#2, `docs/mockups/`): calm and text-led, an agenda by day. It is `assets/site.css`, the core's, every rule under `.events-site` (`AssetsTest` holds it to that) and the layout by container queries on `.events-site`, not the window, so that it fits a theme's column. Its colours are custom properties on `.events-site`, and every pair read together passes WCAG AA (`ContrastTest`, which reads them from the file). The standalone frame's own few rules, outside `.events-site`, are `standalone/assets/frame.css`.
- **Its one font is Source Serif 4, served by the site itself** (`assets/fonts/`, OFL, the Latin subset with every weight in one file), so that nothing is loaded from another website. Text is the system's sans.
- **Stylesheets and fonts are sent from `/assets/`** (`Standalone\Assets`), a stylesheet's address carrying a fingerprint of its contents (`?v=`) and every one sent to be kept a year. Only a file of a kind it names, in its folders, is sent.
- **The listing is `Pages\Events`** (#5), `GET /events` 20 to a page (`PER_PAGE`): a form (GET) of words, from and to, a place and a Category, its fields named in the page's language (`field()` in a template). The place is one filter for a Location (its ref) or a Region (`region:` and its ref), `Places` turning it into the API's `location` or `region`; the menu is the Regions with their Locations (`/regions`, `/regions/{ref}/locations`). By date it is grouped by day, the day being an event's first from where the list starts (`EventLines::byDay()`), so a fair begun yesterday is under today; a Search best match first is one line after another with each its own day (`oneByOne()`). A listing narrowed by anything but its page, and every Search, is `noindex` (`Shown::$indexed`): the Location and Category pages are the ones for search engines.
- **An event's page is `Pages\Event`** (#6): `GET /events/{ref}`, `/reviews` and `/comments`, and the Venue's own answer (`/venues/{ref}`) for its coordinates and, once the API gives one, its `address`, an event's `venue` having neither; a Venue gone a moment ago leaves the event shown with its name. Each is kept five minutes. When and where come first in the page, so a phone shows them before anything else, and a wide screen beside it. An event every time of which is over (`When::isOver()`, the API's own meaning of over, against `Asking::now()`) says it has ended and leads to what is coming at its Venue or in its Location; a Cancelled one says so the same way; both keep their Reviews. A description's paragraphs are kept apart by an empty line and its other lines kept (`nl2br` after escaping). Reviews and Comments are the API's first page, newest Reviews first, saying how many more there are. Earlier years' Reviews are under their year, an earlier Edition with none left out. `source_url` is "More information". Text in the other language says so and is marked with `lang`.
- **A Venue's page is `Pages\Venue`** (#7): `GET /venues/{ref}`, which holds its coming events too, shown by day as the listing's lines, each event's name a heading below its day's (`name_level` in `parts/event-line.twig`) and saying nothing of where it is, the page being where. Where it is (its `address` once the API gives one, its Location, a map link at its coordinates), how to reach it (phone as `tel:`, email as `mailto:`, website by its short address) and its social links come first, as the event's facts do. What it does not have is left out, never said to be missing. With nothing coming it says so and leads to its Location.
- **Only a web page's address is ever linked** (`Text::webAddress()`: `http` or `https` and a valid address), whoever wrote it: a Venue's website and social links, an event's `source_url`. A `javascript:` or `data:` address is not linked, and a social link with one is left out. `Text` also holds what other people's text needs: `paragraphs()`, `summary()` (a page's description, about 155 letters, cut at a word), `dialled()` and `mailed()`.
- **A text in the other language** is marked with `lang` wherever it is shown, and only a description is remarked on ("There is no English text…"): a name in the other language is still its name.
- **Numbers are written by `Numbers`**: a price with two decimals when it has cents, a rating with one, each as the language writes it.
- **Each Location's and each Category's page is the listing with that filter fixed** (#8): `new Events(Events::LOCATION)` and `Events::CATEGORY`, at `/es/eventos-en/{ref}` and `/es/categoria/{ref}`. The address's ref is the filter, and that field is left out of the form, whose action, pager and "See everything" stay on the page; a `place` or `category` in its query is ignored. Its heading, title and description name it ("What's on in Motril", "Film: what's on along the coast"), from the reference lists; a ref that is neither is not found before any event is asked for. A Region has no page. These are the pages for search engines: indexed as they stand, `noindex` once narrowed further. The listing's lines link their Venue, Location and Categories to their pages.
- **What the API refuses is `Api\Refused`**: a 422 with the fields it names, said beside each field in the site's own words (`events.refused.*`), the API's being English only; and a 429, asking too often, said over the form. Neither is kept or logged. Anything else not 200 is `ApiFailed`.
- **Lines of events are `EventLines`**, from the API's `EventSummaryResource`: when (a time, or "All day"), where (Venue and Location), until the last day of a run, how many more dates, the price (two decimals when not whole), the Categories, the rating with how many Reviews, Cancelled (the event's status or its first time's), and its photo, the description being its `alt`. A name in the other language has `lang`. `parts/event-line.twig` shows one; a line with a photo has the class `with-photo`, so that one without has no empty column. Numbers are written as the language writes them (`4,50`).
- **Days and times are `When`**, from the API's own strings, the names of days and months in the language files: `heading()` for a day over a list ("Martes 27 de octubre", its year when not this year's), `day()` within a sentence, `short()` and `dayAndTime()` for a line with its own day. Nothing is moved to another time zone. Today is today in Spain by the site's clock (`Asking::today()`), which `Site` takes so that a test can set it.
- **The frame has a skip link** to `#content`, and every link and field shows the focus outline (`--focus`).

## Tests

- **Pages are tested against saved answers** (`tests/answers/`, served by `Tests\Support\SavedApi`), captured from the real API in its known test state by `bin/capture-answers.php` and never written by hand. A page that asks something new adds the question to `tests/answers/questions.php` and captures again.
- **The known state's days are counted from the day it was made**, so the capture writes that day to `tests/answers/today.txt` and `Tests\Support\Browsing` sets the site's clock to noon of it (`$day` and `$time` set another). A test that visits pages uses that trait, and writes a day it expects with `written()`, counted from the capture (`inDays()`), never as a fixed date: the next capture would break it. `WhenTest` holds the words for days to fixed dates.
- **What the known state cannot show** (a price, a photo, a cancellation, pages beyond the first) is a saved answer changed and given with `SavedApi::instead()`, never one written from nothing, so that its shape stays the API's. `instead()` also takes a `Refused` to throw.
- **`StandInApi` and `FailingApi`** are for what saved answers cannot show: what was asked, and an API that fails.
- **`bin/with-local-api.php` gives the API `null` for every outside service's key**, not '': on Windows PHP's `proc_open` drops a variable that is empty, and the API then used the key in its own `.env` and asked Voyage for real (found on 2026-10-27, when the saved Searches said `hybrid`).
- **`CurlApiTest` starts PHP's own server** with `tests/fixtures/echo-api.php` to see what curl really sends.
- **The `real` suite** (`tests/Real/`) compares each saved answer's shape with the live API's, run through `bin/with-local-api.php`. It is run before a deploy and is not part of the default suite or of GitHub Actions.
- **On Windows**, a command given to `bin/with-local-api.php` that is a PHP script is run with PHP; the API server it starts is stopped whatever happens, since left running it holds the command's output open.
